> Answering the user's question: "Actually, I think it could just be used directly as a survival datapack? What do you think?"
> Conclusion: yes, and it already does "take over the moment you install it". The one thing that must happen automatically (disabling vanilla natural spawning) is built in;
> if you want to manage it yourself, one command steps aside. Below are the assembly steps, the switch list, real-hardware numbers, and exactly what still differs from vanilla.

## 1. Install in Three Steps

| Step | Action | Notes |
|---|---|---|
| ① | Put the `doom.nats/` unzipped from `dist/doom.nats-v4.31.0.zip` into `<save>/datapacks/` (on a server, `world/datapacks/`) | The automated installer `src/tools/install.mjs` (needs a local save / server) |
| ② | `/reload` after entering the world | A pack newly placed in the world directory doesn't require quitting and re-entering (source: `ReloadCommand.discoverNewPacks` → `PackRepository.reload()`) |
| ③ | See `[nats] mode/survival —— 已接管自然生成（doMobSpawning=false）` in chat / the server log | Seeing it means it's in place; if not, check `logs/latest.log` for load errors |

Why step ① doesn't require you to worry about "disabling vanilla": this pack creates mobs with `summon`, which `doMobSpawning` can't touch.
If vanilla natural spawning is still on, you get double spawning, and the distribution, capacity, and performance all go out of control.
So `core/setup` (the load tag) runs `mode/survival` directly and turns `doMobSpawning` off.
It only disables "natural spawning"; spawners / structure generation / breeding / command summons / spawn eggs are all unaffected.

## 2. Switches and Commands (All Typable in Chat, Also Callable from Command Blocks/Maps)

| Command | Purpose |
|---|---|
| `function doom.nats:mode/survival` | Survival-ready: `gamerule doMobSpawning false` + immediately emit an environment snapshot (run by default on load) |
| `function doom.nats:mode/manual` | No longer auto-change the gamerule on future loads (left to you / the map; the switch state lives on the scoreboard and survives `/reload` and re-entering the world) |
| `function doom.nats:mode/auto` | Restore the default (auto-takeover on load) |
| `function doom.nats:mode/off` | Step aside: silently clear this pack's mobs + `gamerule doMobSpawning true` |
| `function doom.nats:debug/clear` | Clear the field only (silent removal via `util/void_kill`, no drops and no experience) |
| `function doom.nats:debug/density` | See the density control state: target/minute, last minute's actual, `$eff.batch`, case cadence, current cap |
| `function doom.nats:debug/env` | Environment snapshot: players / loaded chunks / weather / phase / dimension |
| `function doom.nats:debug/reject_report` | Attribution histogram (reason 0..9) + light failure tiers, printed then cleared |
| `function doom.nats:debug/mobs` | Mob registry and per-cluster cap overview |
| `tag @e[type=zombie,limit=1] add doom.nats.persistent` | Mark one mob as "persistent" ⇒ `debug/clear` won't clear it |

Adjusting density: the default is `$eff.batch = 6` (origin points per tick); the case engine automatically changes cadence and caps with rain/thunderstorm/night/dimension/player count/moon phase.
For closed-loop control, set a target:

```
scoreboard players set $density doom.nats 200     # target 200/minute, 0 = off (default)
scoreboard players set $ctrl.maxBatch doom.nats 200
```

Below target, it adds batches; above target by 25%, it shrinks proportionally (AIMD). The measurement source is `$spawned.total`, a cumulative value that is never cleared.

## 4. Performance and Capacity (Measured Locally)

| Metric | Measured |
|---|---|
| Steady-state monster count | 71.7 (cap 70, peak 77); the capacity chain really is in charge |
| mspt | mean 5.29 / peak 5.70 (budget 50) |
| Refill after a full clear | 70 → 26 within 2 seconds, back to 70 in about 6 seconds |
| Source of the throughput ceiling | Not performance, but vanilla's `maxCommandChainLength` (default 65536 ≈ 10 attempts/tick) |
| After raising it to 1,000,000 | batch 40 → 9.7 ms; 160 → 24.1 ms; 400 → 50.9 ms (over budget) |

Recommendation: to keep mspt under 30 ms ⇒ on this machine, `$eff.batch` should not exceed 200.
For higher density on a custom map, raise `maxCommandChainLength` before raising batch — don't eat up the frame budget.

## 5. Differences from Vanilla (Honest List — Don't Treat It as "Fully Identical")

From the mechanism coverage table in `docs/14`, reordered by real survival impact:

### Already Replicated to the Letter of the Source

| Aspect | Notes |
|---|---|
| Global mobcap | `maxInstancesPerChunk × spawnableChunkCount / 289`, integer division, strictly less than (`spawnableChunkCount` is the measured 17×17 loaded union, not an estimate) |
| Per-player cap | Uses `maxInstancesPerChunk` itself, OR semantics |
| Cluster model | At most 3 groups per attempt; the group origin resets per group; in-group movement accumulates `nextInt(6)-nextInt(6)`; the species is drawn once per group; `groupSize = minCount + rand(1+max-min)`; `spawned ≥ getMaxSpawnClusterSize()` ⇒ ends the whole attempt (default 4; only 8 entity classes override it) |
| Despawn | Hard despawn at 128 blocks (64 for aquatic) + probabilistic despawn (denominator scaled to 1/40 per 20 ticks, equivalent to vanilla's 1/800 per tick); uses `void_kill`'s discard semantics |
| Biome spawn table | 65 biomes, 769 rows, point-for-point equivalent to vanilla's `WeightedRandom` |
| Per-entity placement | Rules 0..4: generic / water-surface aquatic / deep water / bat (below surface + brightness + 50%) / slime (50<y<70 + moon phase + brightness) |
| Case engine | rain / thunderstorm / night / dimension / player count / moon phase → cadence and caps |

### Approximations (Usable, but Don't Compare It Cell-by-Cell Against Vanilla)

| Aspect | Gap |
|---|---|
| Light | Can only approximate with 5 tiers (the predicate can't read the brightness value); vanilla samples and compares `uniform(0..7)` |
| Player exclusion zone | Vanilla is 24 blocks; this pack approximates with a 27-block lower bound |
| Multiplayer chunk union | Exact in singleplayer; multiplayer uses two square approximations (Euclidean distance expressions can't be written in a datapack) |
| Collision boxes | Approximated with block tags, not true AABBs |
| `spawn cost` | Simplified to `Σ(1/r) ≤ budget/q²`, a 4-bucket approximation; only applies to `warped_forest` / `soul_sand_valley` (vanilla is also non-empty only in those two) |
| Placement y | Can't read the heightmap ⇒ follow the player ± jitter, or a fixed band declared by the map |

### Not Done (Gaps — Written Here Rather Than Pretending to Be Equivalent)

| Aspect | Impact |
|---|---|
| Structure spawning priority | Fixed tables such as nether fortresses don't take effect |
| `finalizeSpawn` group data | Chicken jockeys, sheep color following the biome, etc. don't take effect |
| Slime chunks (the y<40 rule) | Only spawns at 50<y<70 per vanilla rules; below 40 it doesn't spawn (a datapack can't compute chunk-level RNG unless the map author declares it in advance) |
| Regional height band | `pos/band` is still a placeholder implementation (`storage doom.nats:bands` isn't wired up yet); custom map authors need to declare it first |

> In one sentence: it's fine to play as survival; "cell-for-cell identical to vanilla" would need a mod layer to take over `NaturalSpawner`, which a datapack can't reach.

## 6. Uninstall / Rollback

```
function doom.nats:mode/off      # clear the field + hand natural spawning back to vanilla
```
Then delete `datapacks/doom.nats` and `/reload`.
Note: mobs already spawned won't vanish because you deleted the pack (they're just ordinary mobs); if you need to, run `debug/clear` first —
`doom.nats:mode/off` has already done that step.

## 7. Two More Things Custom Map Authors Must Do

1. Declare the height band: set `$band.mode = 1`, and change `$band.yMin / $band.yMax` (writing `storage doom.nats:band` as well) to the map's actual spawn band.
2. Calibrate the block tags: `node src/tools/propose_tags.mjs` reads the map's Anvil region files directly and produces an override proposal for `#doom.nats:standable` / `#spawnable_at`.
   For reference: on the test terrain (snowy), 40% of the surface is ice-family blocks; after adding them to the tag, coverage went from 3.7% → 43.9%, `spawnable_at` reached 100%, and the adoptable suggestions dropped to zero.

## 8. Changes in v4.14 (Three Survival-Related Ones)

| Change | Notes | Impact on survival |
|---|---|---|
| Animals finally spawn | Previously all species shared a "dark ≤ 7" light tier, while animals require "bright ≥ 9" ⇒ contradictory, so they never spawned | In daytime (or in the open at night) you'll see sheep/cows/pigs/chickens etc.; biomes like `snowy_beach` that have no creature list still don't spawn (same as vanilla) |
| Dimension parameters are taken per dimension | Sea level 63/32/0, light tiers per dimension; the dimension is detected at the first player's position | After entering the Nether/End, spawn parameters follow automatically (previously they kept using Overworld parameters) |
| Everything is configurable | `storage doom.nats:config` overrides sea level/light/capacity/distance/cadence/density/despawn/persistence/height band | To change intensity, keep mobs around, or pin a height band, you don't need to modify the pack: `data merge storage …` + `function doom.nats:cfg/apply` (see `docs/18-配置手册.md`) |

Two more directly relevant to survival:

- Despawn: what this pack spawns are ordinary mobs, and vanilla's own despawn logic (128 blocks / 1/800 after a minute) is already in charge of them;
  our own dice layer is off by default (`dice:0`), so despawns are no longer faster than vanilla.
- Persistence: `tag @e add doom.nats.persistent` only affects this pack's clearing and despawn layers (keeping mobs alive);
  to make vanilla not despawn them either, use `PersistenceRequired:1b` (or set `persist` to 1).
