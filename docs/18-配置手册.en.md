# 18 · Configuration Manual ("All Spawning Must Be Definable", v4.14)

中文: `docs/18-配置手册.md`

> Goal: gather all the numbers previously scattered across the generators into a configuration layer that maps/datapacks can override;
> every cell of spawn behavior (pick-point height, category capacity, distance, tick, light tier, sea level, persistence, block tags, per-entity rules)
> can be declared or rewritten by the author. This document is the list of all knobs, with sources.

---

## 1. The Three-Layer Configuration Model

| Layer | Location | Who writes | Note |
|---|---|---|---|
| Default layer | `storage doom.nats:cfg_defaults` | This pack (rewritten on every load) | Values = vanilla semantics (sources in the table below); do not hand-edit |
| Override layer | `storage doom.nats:config` | Map/author (write only the keys you want to change) | Does not need to be complete; missing keys fall back to the default |
| Recomputation layer | `$cfg.*` scoreboard | `cfg/apply` | All other layers only read `$cfg.*` (refreshed every tick with the dimension) |

How to write:

```mcfunction
# Override only the keys you want to change (the rest stay as they are)
data merge storage doom.nats:config {seaLevel:{overworld:64}, cap:{monster:120}, band:{mode:1, yMin:70, yMax:90}}
function doom.nats:cfg/apply          # takes effect in the overworld/the current player's dimension
function doom.nats:cfg/apply_here     # first detects the dimension of the execution position, then recomputes (for author review)
```

- `cfg/apply` reads `$snap.dim`, written every tick by `circ/snapshot` (probed at the position of the first non-spectator player);
- `cfg/apply_here` probes the dimension at the current execution position (`execute in minecraft:the_nether run function doom.nats:cfg/apply_here`);
- Both merge the default layer with the override layer, with the override layer taking priority.

> ⚠ `data merge` is a shallow merge: `{cap:{monster:120}}` changes only `cap.monster`; other `cap.*` keys keep their defaults.

### 2.2 Category Capacity and Distance

| Key | Default | Vanilla source |
|---|---|---|
| `cap.monster` | `70` | `MobCategory.MONSTER(70, …)` |
| `cap.creature` | `10` | `MobCategory.CREATURE(10, …)` |
| `cap.ambient` | `15` | `MobCategory.AMBIENT(15, …)` |
| `cap.water_creature` | `5` | `MobCategory.WATER_CREATURE(5, …)` |
| `cap.water_ambient` | `20` | `MobCategory.WATER_AMBIENT(20, …)` |
| `cap.underground_water_creature` | `5` | `MobCategory.UNDERGROUND_WATER_CREATURE(5, …)` |
| `cap.axolotls` | `5` | `MobCategory.AXOLOTLS(5, …)` |
| `distance.monster` … `distance.axolotls` | `128` (`water_ambient` is 64) | The 5th constructor parameter = `despawnDistance` |
| `noDespawnDistance` | `32` | `MobCategory.noDespawnDistance` (closer than this resets `noActionTime` to 0) |
| `playerExclusion` | `24` | `NaturalSpawner.isRightDistanceToPlayerAndSpawnPoint`: `distSq ≤ 24²` rejected |
| `spawn24` | `0` (off) | The second branch of the same check: `getSharedSpawnPos().closerToCenterThan(pos, 24)` rejected. A datapack cannot read the spawn point ⇒ the author must declare it (see 2.2b) |
| `spawnX` / `spawnY` / `spawnZ` | `0` | Block coordinates of the world spawn (integers). Effective only when given together with `spawn24:1` |

Global capacity algorithm (copied verbatim, not configurable): `cap = cap.<category> × spawnableChunkCount / 289` (integer division, strict less-than);
`spawnableChunkCount` is measured by `circ/snapshot` as the 17×17 union of `execute if loaded`.

Counting convention (v4.14d, aligned with vanilla `SpawnState.createState`): counting is done in the player's dimension, by
`type=#doom.nats:<category>` (complete vanilla category membership), skipping mobs with `nbt={PersistenceRequired:true}`.
⇒ Same-category mobs generated by spawners / structures / commands / other datapacks all consume quota (consistent with vanilla).
Category tags can be regenerated with `node _work/extract_categories.mjs` (source = the `EntityType` registration block).

Real-machine experience with dimension scoping (v4.14g/h):
① An `@e` without coordinate/volume constraints selects entities across dimensions (`execute in <dimension>` does not help). To scope it you must add
   `distance=..N` or an `x/dx/y/dy/z/dz` box; that is what this pack's per-dimension counting does.
② A spawn attempt must run in the player context (`core/tick`'s context is the world spawn). Otherwise absolute-coordinate positioning lands in the overworld,
   and nothing ever spawns when the player is in the nether/end. Implementation: `spawn/try → spawn/try_at`.

### 2.2b World Spawn 24-Block Exclusion (v4.17 · P1-5)

Vanilla `isRightDistanceToPlayerAndSpawnPoint` checks two things at once (1.21.6 named line 208):

```java
if (distSq <= 576.0) return false;                                        // ① player within 24 blocks ⇒ this pack's reason=1
else if (level.getSharedSpawnPos()                                     // ② world spawn within 24 blocks
             .closerToCenterThan(new Vec3(pos.getX()+0.5, pos.getY(), pos.getZ()+0.5), 24.0)) return false;
```

② cannot be read by a datapack: the `spawn` field of `level.dat` has no predicate/command to query it, and the `SpawnX/Y/Z` in player NBT is the bed/respawn anchor
(once you sleep, it diverges from the world spawn). So it can only be declared by the author, and is off by default:

```mcfunction
# Example: world spawn at (-128, 64, 320)
data merge storage doom.nats:config {spawn24:1, spawnX:-128, spawnY:64, spawnZ:320}
function doom.nats:cfg/apply
```

- Enabling requirement: `spawn24=1` and all three axis coordinates declared. Missing any axis ⇒ `cfg/apply` forces `$cfg.spawn24` back to `0`
  (otherwise the default `0,0,0` would be treated as the spawn point and ban the whole 24-block area around the world origin);
- The check is equivalent to vanilla's floating-point form (including the `+0.5` half-block offset of the `BlockPos` center): the integer form `4d² = 4dx² + (2dy+1)² + 4dz² < 2304`,
  with exactly 24 blocks not counting as a rejection (consistent with the source's `<`);
- Failure attribution: `reason=10` (histogram `[nats.reject] rej: … 10=<n>`; the original 0–9 encoding is in `spawn/emit` → `debug/reject`);
- Candidate point coordinates use `$wx / $py / $wz` (the current walk point maintained by `spawn/walk`), not the biome snapshot point;
- The old behavior of not reading the spawn point (= this check not taking effect at all) remains an optional "known deviation", see docs/19 Q1.

Red-to-green record (two real-machine-class pitfalls, both discovered by this check itself):

1. The gate must not be written as `execute unless data …`. The offline interpreter (`tools/lib/interp.mjs`'s `evalCondition`) has no `data` branch,
   so `unless data storage …` is judged "true after negation" and the following `storage` is treated as a subcommand ⇒ `sim_v4`'s `no-error`
   went from 27 PASS/0 FAIL to 24/3 (`execute subcommand storage` ×3, amplified by every cfg/apply call). Changed to
   `set 0 → execute if data storage … run set 1 → multiply the three axes`, which restored 27/0 (with identical real-machine semantics).
2. Tests must first align the "execution dimension". `@a[distance=…]` selects players by the execution dimension: when the robot is in the nether,
   `execute positioned … run function check/distance` in the overworld degenerates to `reason=2` because "there is no player in this dimension", and all 8 assertions go red.
   `_work/verify_spawn24.mjs` reads the player's `Dimension` first every time, then does `execute in <dimension> positioned …`.

|---|---|---|---|

| `special` | `-1` | — | Regional difficulty multiplier percent (`DifficultyInstance.getSpecialMultiplier()`'s 0..1 × 100). `-1` = automatic: derived from `difficulty` as a mature-world approximation (normal 75, hard 100; easy/peaceful 0). ### 2.4 Point Picking (Height Band)

| Key | Default | Note |
|---|---|---|
| `band.mode` | `0` | `0` find the ground automatically · `1` random within a fixed band · `2` follow the player ± jitter · `3` uniform random band (closest to vanilla `uniform(minY, surface+1)`) |
| `band.yMin` / `band.yMax` | `60` / `70` | The interval for modes 1/3 (when `min == max` that value is used; degenerate intervals are guarded) |
| `band.jitter` | `3` | Jitter radius for mode 2 |

> Vanilla point picking: x/z uniformly random within an eligible chunk, y uniformly random in `[minY, surface+1]` (`Mth.randomBetweenInclusive`).
> A datapack cannot read the heightmap ⇒ mode 3 is the closest approximation as "author-declared interval + uniform random"; mode 0 uses a 19-layer downward scan to find a standable surface.

### 2.55 Structure Spawn Priority (Nether Fortress)

When `spawn/pick_one` hits the combination "nether ∧ below is `minecraft:nether_bricks` ∧ inside a `minecraft:fortress` structure",
the fixed table `mob/fortress` (= vanilla `NetherFortressStructure.FORTRESS_ENEMIES`, weights summing to 28) replaces the biome table.
The fortress path sets `$cost.threshold` to 0 (no spawn cost). To switch to other structures/lists, change the
`FORTRESS` array in `gen_mobs.mjs` and the `structures` list in `predicate/spawn/in_fortress.json`.

### 2.6 Per-Entity Rules (the "definability" of rules)

The data source for the rules is one table: `src/tools/lib/entity-rules.mjs` (47 entities → 27 rule signatures),
written at generation time to `doom.nats/_work/generated/entity-rules.json` (containing each rule's semantic fields),
then shared by `gen_mobs.mjs` (writes the roster's `$sel.*`) and `gen_check.mjs` (generates `check/block` / `check/entity`).

To change an entity's rule there are two ways:

1. Edit the table and rebuild (recommended): edit `lib/entity-rules.mjs`, then
   `node src/tools/gen_mobs.mjs && node src/tools/gen_check.mjs` (or run the whole pack's `--check` regression).
2. Rewrite the roster at runtime: `data merge storage doom.nats:sel {…}` only changes "this one attempt";
   to persistently change a biome/category's species table, rewrite the corresponding `<biome>/<category>` function (it also writes fields such as `$sel.rule`).

Rule fields (one rule = one signature):

| Field | Values | Semantics |
|---|---|---|
| `place` | `ground` / `any` / `water` / `water_surface` / `below_tag` / `lava` | Corresponds to `SpawnPlacementTypes`' ON_GROUND / NO_RESTRICTIONS / IN_WATER / IN_WATER + water surface window / ON_GROUND + dedicated tag / IN_LAVA |
| `light` | `none` / `dark` / `bright` / `bat` / `slime` / `glow` / `bl8` | Per-entity light requirement (§4) |
| `tag` | vanilla block tag | Block below (animal family) |
| `coins` | `half` / `moon` / `2of3` / `1of15` / `1of20` / `1of40` | Random rejections in vanilla predicates |
| `sky` / `noSky` | bool | Husk/stray require `can_see_sky`; guardian is `1/20` or underwater with no view of the sky |
| `notWart` | bool | Block below is not a nether wart block (zombified piglin/piglin/hoglin) |
| `deep` | bool | Drowned `y < seaLevel-5` (1/15 in `#more_frequent_drowned_spawns` biomes) |
| `river98` | bool | water_ambient does not spawn 98% of the time in river biomes |
| `d64` | bool | water_ambient must be ≤ 64 from the player |
| `ySea` / `yTurtle` | bool | Glow squid `≤ seaLevel-33` / turtle `< seaLevel+4` |
| `lavaToAir` | bool | Strider: lava above up to air |
| `grp1` | bool | Tropical fish of a non-schooling variant ⇒ only 1 per group |
| `cluster` | int | `getMaxSpawnClusterSize` (default 4) |
| Dimensions (automatic) | width/height | Extracted from `EntityType.Builder.sized(w,h)` (`_work/generated/hitboxes.json`): width>1 ⇒ check four neighbors, width>2 ⇒ check ±2, height>2 ⇒ check the third block (corresponds to vanilla `noCollision(getSpawnAABB)`) |
| `persist` | bool | This species carries `PersistenceRequired:1b` |

## 4. Lighting (Per-Entity, Fixed in v4.13)

| Tier | Criterion | Vanilla equivalent |
|---|---|---|
| `none` | No check | Magma cube/ghast/piglin family/ocelot/strider/aquatic family/glow squid (each has its own rule) |
| `dark` | Combined brightness ≤ the `light.<dimension>` tier | `Monster.isDarkEnoughToSpawn` |
| `bright` | Combined brightness ≥ 9 or can see sky | `Animal.isBrightEnoughToSpawn` (approximation of raw brightness > 8) |
| `bat` | ≤ 3 (7 on Halloween) + 50% | `Bat.checkBatSpawnRules` |
| `slime` | ≤ 7 + 50% + moon phase | `Slime.checkSlimeSpawnRules` |
| `glow` | == 0 | `GlowSquid.checkGlowSquidSpawnRules` |
| `bl8` | ≤ 8 | `PatrollingMonster.checkPatrollingMonsterSpawnRules` |

Known approximation: vanilla is a sampling comparison "brightness ≤ `random.nextInt(N)`" (lower is more likely to pass); a datapack's predicate can only test by tier.

## 5. Persistence (`PersistenceRequired`) Three States

| State | Who sets it | Vanilla behavior | This pack's cleanup/despawn layer |
|---|---|---|---|
| Default (this pack's spawns) | Nobody | `Mob.checkDespawn` manages normally: hard despawn at 128 blocks + a 1/800 roll every tick once `noActionTime>600` | Both `debug/clear` and the built-in despawn layer handle it |
| With the `doom.nats.persistent` tag | Author/map (`tag @e add …`) | Not recognized (this is this pack's own tag; the mob is still an ordinary mob ⇒ it despawns anyway) | The cleanup and despawn layers skip it |
| With `PersistenceRequired:1b` | Per-rule `persist: true`, or globally `$cfg.persist=1` | `checkDespawn` returns immediately ⇒ never despawns | The cleanup and despawn layers skip it |

```mcfunction
# Example: make one mob stay forever (vanilla semantics)
data merge entity @e[type=zombie,limit=1] {PersistenceRequired:1b}
# Example: only let this pack's cleanup/despawn layer leave it alone (vanilla will still despawn it)
tag @e[type=zombie,limit=1] add doom.nats.persistent
```

> Reference: the vanilla paths that make a mob "naturally persistent" include: name tags (`NameTagItem`), structure generation (ocean ruins/swamp huts/woodland mansions),
> riding (`requiresCustomPersistence = isPassenger()`), `setItemSlotAndDropWhenKilled` (mobs that always drop their equipment), and so on.
> This pack does not add these (it keeps the "ordinary mob" semantics).


## New in v4.19: Point-Picking Fallback (Uniform y Over the Whole Column, Vanilla-Style, in Deep Water / While Floating)

| Key | Default | Note |
|---|---|---|
| `band.fallback` | `1` | Whether mode 0 "automatic ground scan" falls back to vanilla-style uniform point picking over the whole column when it cannot find ground. `0` = old behavior (clamped to the player's layer) |
| `floorY.overworld` / `.the_nether` / `.the_end` | `-64` / `0` / `0` | Lower bound of the fallback interval (= vanilla `Level.getMinY`). Fallback interval = `[floorY, player layer+2]` |

Background: in vanilla `NaturalSpawner.getRandomPosWithin`, y is uniformly random over the whole column `[minY, surface height+1]`.
When the player floats above deep ocean, the dozen blocks under water are still candidate points. This pack's mode 0 scans for ground only within "player layer +2 .. -16"; in that window above deep water
there is no standable layer at all ⇒ candidate points are pinned to the player's layer ⇒ the drowned's `isDeepEnoughToSpawn` (`y < seaLevel-5`) never passes,
and the water surface window (place 3) requires water above too ⇒ zero spawns in deep water (no drowned, no fish, no squid).
The fallback triggers only when "mode 0 ∧ no ground found ∧ `fallback=1`"; on land, ground is found ⇒ behavior is completely unchanged.
Some fallback points land inside stone and are rejected by `check/block`, isomorphic to vanilla's "you only know once you draw".

```mcfunction
# Turn the fallback off (restore the old behavior)
data merge storage doom.nats:config {band:{fallback:0}}
function doom.nats:cfg/apply
# Change the nether (e.g. a map lowers the overworld's floor further)
data merge storage doom.nats:config {floorY:{overworld:-128}}
function doom.nats:cfg/apply
```

## Appendix: Runtime Editing (v4.24): "Change storage and It Takes Effect Immediately, No Regeneration"

The earlier sections of this chapter are all build-time/load-time knobs (`$cfg.*` is recomputed by `cfg/apply` and takes effect on load).
v4.24 pushes "customizable" one step further: change storage at runtime, and the checks read it on the spot — no regenerating the pack, no reinstall, no restart.

### 1. Two Paths That Do Not Conflict

| | Build time (v4.23) | Runtime (v4.24) |
|---|---|---|
| Entry point | `rules/entity-rules.json` · `entries.json` · `counts.json` | `storage doom.nats:author` (shape isomorphic to the three JSON files) |
| How it takes effect | Edit the file → run the generators → reinstall/`/reload` | Change storage; the next check already sees the new value (no `/reload` needed; `function doom.nats:author/load` only refreshes the summary cache) |
| Limits | None (expanded at generation time) | Entries ≤8 · Y segments ≤8 · placement-surface tags ≤8 · biome lists ≤4 each (runtime slots are fixed) |
| Command surface | None (edit files) | `author/{help,show,load,reset,export,demo,add_entry,add_below_tag,set_group_by_y,set_cap_y}` |

> Three layers of identity: ① vanilla reproduction (default; empty `rules/` + empty storage ⇒ identical to vanilla entry by entry)
> ② this pack's extension (stable): all the capabilities in the table above
> ③ experimental (non-vanilla): the `near` relation condition / the `on_spawn` presentation hook / the `preset` preset, only in the experimental variant `v4x`,
> with artifacts landing in `doom.nats:exp/*` (functions), `doom.nats.exp.*` (entity tags), `doom.nats:exp` (storage).

### 2. Field-by-Field List

The same table as `rules/README.md` §7 (that is the main manual):

- `entityRules.<entity id>`: `belowAny`(≤8) `yMin` `yMax` `lightMin` `lightMax` `weather` `biomeIn`(≤4) `biomeNot`(≤4) `place` `light` `persist`
- `entries[]` (≤8): `id` `mob` `biome` `category` `weight` `min` `max` `nbt` `when{thundering,raining,yMin,yMax,lightMin,lightMax}`
  ⚠ `weight`'s hit rate is ≈ `weight / 1000000`, not "proportional competition in the same pool as vanilla". To take effect, fill in six-digit values; a number like `40` is equivalent to not spawning.
  When several exist at once, look at the sum: Σweight should be ≤ `1000000`, otherwise later entries never hit (each entry consumes its interval of `0..999999` in declaration order;
  e.g. four entries each with `900000` leave only the first alive; they should each be `200000`). For a comparison table see [`wiki/规则字段参考.md`](wiki/规则字段参考.md)
- `counts.groupByY.<entity id>[]` (≤8 segments): `{yMin?,yMax?,min,max}` (later segments override earlier ones)
- `counts.capByY.<category>[]` (≤8 segments): `{yMin?,yMax?,max?,localMax?}`

The reason codes on rejection match the build-time/vanilla ones: placement surface ⇒ `3` (light)/`4` (block), other rules ⇒ `9`, capacity ⇒ `5`.

### 3. The Experimental Variant and Its Two Switches

1. Engine gate (whole-pack level): the experimental variant `dist/doom.nats-v4x-experimental-v4.30.0.zip` (its extracted `doom.nats/`) has a `pack.mcmeta` declaring
   `"features": {"enabled": ["minecraft:minecart_improvements"]}` (1.21.6 has no "custom datapack" flag,
   so it borrows a native experimental flag; the price is that worlds enabling it also get vanilla's minecart changes).
   When the world has not enabled that experimental feature: on the client's pack list it is incompatible/unselectable, and the server's `/datapack enable` refuses explicitly:
   `Pack 'file/doom.nats' cannot be enabled, since required flags are not enabled in this world: minecraft:minecart_improvements!`
   (real-machine log; note that `/reload` bypasses this gate, so for official releases go by the "world load state".)
2. Runtime switch: `storage doom.nats:exp enabled:1b`, toggled with `function doom.nats:exp/{enable,disable}`.
   Off = the whole layer takes no part in the checks (the entries remain), and behavior returns to the stable layer/vanilla.

```mcfunction
function doom.nats:exp/add_entry with storage doom.nats:exp_in
```

## Appendix: Experimental AJ / Third-Party Rig Toolchain Rig Bridging (from v4.25 · Source Exists, Not Shipped With the Builds): How to Hook Up "Custom Mob Appearance"

> This layer is not in the default artifacts, nor in the three experimental builds v4.25 / v4.28 / v4.29: the generator `tools/gen_exp_aj.mjs`'s contract is that if `rules/rigs.json` is empty/missing it produces no files at all (and clears the `exp/aj/**` left by the previous run), and this repository's `src/rules/rigs.json` is exactly `{}`. Measured on `dist/doom.nats-v4x-experimental-v4.30.0.zip` (771 entries): 0 entries matching `exp/aj` (v4.25's 765 entries likewise 0), and `pack/doom.nats-experimental/` also 0 ⇒ this layer needs `gen_exp_aj.mjs` to take part in the build, and neither build ships it; to use it, write your own non-empty `rules/rigs.json` (an example is in `rules/examples/aj/rigs.json`), then rerun `tools/gen_exp_aj.mjs` with `DOOM_EXP=1` (together with `gen_pack.mjs` / `gen_mobs.mjs`), and only then will `doom.nats:exp/aj/**` (17 files) be produced.
> Engine gate: v4x's `pack.mcmeta` declares `{"features":{"enabled":["minecraft:minecart_improvements"]}}`
> (the feature flags available in 1.21.6 are only `minecart_improvements` / `redstone_experiments` / `trade_rebalance`,
> there is no "custom datapack" flag; the `minecraft:update_1_21` written in the SPEC does not exist in 1.21.6; the price of borrowing this flag is that
> worlds enabling it also get vanilla's minecart changes). If the world does not enable this flag ⇒ the engine refuses to load v4x outright (refusal is more reliable than a warning).

| What you want to do | Where to write it | Note |
|---|---|---|
| Give a species a third-party skeleton | Add a `{carrier, rig, …}` entry to `rules/rigs.json` | Field table in `rules/README.md` §8; regenerate with `DOOM_EXP=1` after editing |
| Invisible/silent/AI-less core | That entry's `carrier_nbt` | For example `{Silent:1b,active_effects:[{id:"minecraft:invisibility",…}]}` |
| Start a third-party animation | That entry's `on_spawn` | Called after mounting completes (`@s` = the core), e.g. `your_rig:start_animation` |
| Core does not count toward mobcap | That entry's `count_with_carrier: false` | Gives the core `PersistenceRequired:1b` (vanilla semantics: persistent mobs are not counted in `SpawnState`; price = immune to the despawn layer/`debug/clear`) |
| Summon only the appearance, without this pack managing it | That entry's `mount: false` | Not claimed/not mounted/not in the sweep layer (for when a third party manages the lifecycle itself) |
| Runtime self-check | `function doom.nats:exp/aj/help` / `status` | How many displays are on the field, how many are mounted, how many are left over (these two functions exist only after you build your own pack containing `exp/aj/**`; none of the v4.25/v4.28/v4.29 builds have them) |
| Zero-dependency regression | `function doom.nats:exp/aj/placeholder/summon` | Hand-make a display skeleton to tell "the bridge is broken" apart from "some third-party rig is broken" (also needs your own build; example config `rules/examples/aj/rigs.json`) |
