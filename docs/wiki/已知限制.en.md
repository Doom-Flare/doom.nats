# Known Limitations

中文: `docs/wiki/已知限制.md`

First, three things it clearly cannot do, so you do not waste time trying:

| What you want to do | Why it cannot be done |
|---|---|
| Brand-new models / textures / AI / pathfinding | A datapack cannot manage client resources, nor an entity's behavior logic. To add a custom mob appearance, the only option is the "real entity as the core + rig as the appearance" bridge (experimental variant); AI and pathfinding cannot be changed. |
| Add mobs to "a biome that originally had no such category" | The biome → species table is world-generation-layer data, and changing it means changing world generation (a `worldgen` override); it is not something a runtime rule can do. |
| Make mobs have causal relationships with each other (for example "spiders eat bugs") | That is a matter of the entity behavior layer (Goal / Brain), and a datapack has no such interface. |

> In one sentence: this pack can only change judgement and counts (where they spawn, when they spawn, how many spawn, what they look like). Client resources, entity behavior, and world-generation structures cannot be changed.

## 1. Approximations (usable, but do not compare them against vanilla block by block)

| Aspect | Gap |
|---|---|
| Light | The predicate cannot read brightness values, so it can only approximate with 5 tier intervals; vanilla samples and compares `uniform(0..7)` |
| Player exclusion zone | vanilla is 24 blocks, this pack approximates with a 27-block lower bound |
| Multi-player chunk union | exact in singleplayer; in multiplayer it uses two square approximations (a Euclidean distance expression cannot be written) |
| Collision box | approximated with block tags, not a true AABB |
| `spawn cost` | simplified to `Σ(1/r) ≤ budget/q²`, a 4-bucket approximation |
| Point-picking height | cannot read the heightmap ⇒ follow the player ± jitter, or a fixed band declared by the map |
| Despawn | cannot read `noActionTime`, so "start rolling once 600 ticks have passed 32 blocks away" cannot be fully replicated; despawn is slightly faster (the roll denominator has been scaled up by cadence to preserve the expectation per unit time) |

## 2. Not Done / Gaps

| Aspect | Impact |
|---|---|
| Slime chunks (the y < 40 rule) | Spawns only at 50 < y < 70 by vanilla rules; below 40 it does not spawn. A datapack cannot compute chunk-level RNG unless the map author declares it in advance |
| Halloween pumpkins | It reads the system calendar, and a datapack has no such interface |
| Regional difficulty / true difficulty | A datapack cannot read it, so it can only be declared through config (`difficulty` / `special`), which goes out of sync with the true difficulty |
| 24 blocks around the world spawn point | Cannot read `getSharedSpawnPos()`, off by default, requires the author to declare coordinates |
| Brain memories / school fish leader / fox target list | Memory items can be written with NBT, but sensor memories are recomputed every tick, and object references and Goal lists are not data |
| Whether passive mobs during chunk generation are covered by `doMobSpawning` | No assumption was made, nor was it verified |
| Restricting spawning by structure ("spawn only inside an end city / fortress") | The author layer has no structure field; the release has no `in_end_city` predicate either (the structures hardcoded at build time are only fortress / outpost / swamp hut / ocean monument / ancient city / trial chamber) ⇒ it can only be expressed with biomes (example: the end outer islands = `end_highlands`/`end_midlands`/`end_barrens`/`small_end_islands`, 4 entries in total) |
| The selected species' vanilla rules on the entry path | **Loaded since v4.32**: `core/setup` calls `mob/load` to write all 47 roster species' `rt` into `doom.nats:mobs`, and `author/entry_rule` writes the whole set into `$sel` whenever the slug is found. The remaining boundary is entities outside the roster (`minecraft:allay` / `minecraft:phantom`, …), which have no `rt` ⇒ they fall back to `rule=0 place=1 light=0 tag=0 cluster=1`. `entityRules` can pin `place`/`light`/`yMin`/`yMax`/`lightMin`/`lightMax`/`weather`/`biomeIn`/`biomeNot`/`belowAny`/`persist`; `tag`/`cluster` still need build time ⇒ for troubleshooting see [[FAQ]] |
| `weight`'s "competition in the same pool" | Does not hold: the measured hit rate is ≈ `weight / 1000000` (the source comment's "proportional within the same pool as vanilla" disagrees with reality) ⇒ for it to take effect, fill in hundred-thousand-scale values. For the mechanism see [[规则字段参考]] |
| `weight`'s total ceiling | Each entry eats its interval across `0..999999` in declaration order ⇒ Σweight is recommended ≤ `1000000`; above that the later entries never hit (a source-level argument; `4 × 200000` has measured corroboration). Example: 4 entries at `900000` each (Σ3,600,000) in practice only the 1st one is alive. See [[规则字段参考]] |

## 3. Capability Boundary (stated plainly)

Using it as a survival datapack is fine; to be "block-for-block equal to vanilla", a mod layer would need to take over `NaturalSpawner`. A datapack cannot reach that precision.

Likewise, the rules that can be changed at runtime have hard upper limits (8 entries / 8 Y segments / 8 landing-face tags / 4 biomes per list), and the source-level switches that decide the shape of the function body (`coins` / `cluster` / `deep` / `sky` and so on) cannot be changed either; those require touching the build-time rule layer.

## 4. What to Do When You Hit a Deviation

1. First run `/function doom.nats:debug/reject_report` to see the rejection reasons (see [[FAQ]])
2. Compare against this page to confirm whether it is a "known approximation"
3. If it is a bug, report it to [Issues](https://github.com/Doom-Flare/doom.nats/issues) with full context (version number / dimension / rejection histogram / `debug/env` output)
